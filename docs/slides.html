A crash course in the basics every developer uses, on the robot and at any job

Quick tour, no memorizing. The goal is that every word on these slides means something to you when you hear it again: compile, Gradle, commit, branch, pull request, CI. There's a one-page cheat sheet to keep.

Every program takes the same trip

Build

Turned into something the computer runs

Each part has a tool. Today is a quick tour of those tools, not a class on any one of them.

This is the map for the whole talk. Everything after this is one of these five boxes. Professional developers do exactly these five things all day, just faster and with more automation.

Files and folders

A project is just a folder

first-robot/
  build.gradle
  gradlew.bat
  vendordeps/
  src/main/java/frc/robot/
    Main.java
    Step1OneMotor.java
  .git/

Folders hold files, and folders inside folders. The path is the list of folders you go through to reach a file.

Your code lives in src/main/java. The package frc.robot is just the folders frc/robot.

The rest tells the tools how to build it. You rarely touch it.

Show this in the IDE's project view and in Windows Explorer side by side: it's the same folder. The .git folder is where version control keeps the history; it's hidden on purpose and you never edit it by hand.

Source code

Code is text written for people

double power = stick * 0.2; // 20% at most
driveMotor.setControl(new DutyCycleOut(power));

A .java file is plain text. You could open it in Notepad.

The computer can’t run text. It runs instructions in a form only it reads.

So something has to translate one into the other. That’s next.

The lines on screen are from Step 1 of the first-robot project: take the stick, scale it to 20%, send it to the motor. The text after // is a comment: the computer ignores it, it's there for the next person reading.

Compiling vs running

Two steps: translate, then run

Main.java

The text you wrote

compile

Main.class

Bytecode: instructions for Java

run

The program

Java runs it, and the motor spins

Compile error

The translation fails: a typo, a missing semicolon. Red underline in the editor. Nothing runs until it’s fixed.

Runtime error

It translates fine, then goes wrong while running: a crash, or the robot does the wrong thing.

Compile errors are the friendly kind: the compiler tells you the file and the line, and nothing bad happens. Runtime errors are the ones that cost you: the code was valid Java but wrong. That's why we have tests and the simulator. Java is compiled to bytecode, then the Java virtual machine runs that; that's why one .class file runs on Windows, Linux, or the robot.

Libraries

Nobody writes it all themselves

A library is code someone else wrote, packaged so your program can use it. A robot program is mostly libraries, with a little of yours on top.

WPILib

FIRST’s library: the robot loop, gamepads, the simulator, field math.

Vendor libraries

From the companies that make the parts: CTRE’s Phoenix for our motors and sensors. Listed in vendordeps/.

Our runtime

The swerve drive, the simulator world and Pitwall, so team code describes the robot.

You don't download these by hand. You write down which ones and which version, and the build tool fetches them. That's the next slide. Versions matter: everyone on the team must build against the same versions, or "works on my laptop" happens.

Gradle

The build tool does the chores

You say what you want. Gradle works out how:

  • download the right Java and every library
  • compile your code
  • run the tests
  • start the program, or send it to the robot

build.gradle

The recipe: which libraries, which versions, which Java.

gradlew.bat

The wrapper: it fetches the right Gradle itself, so nobody installs it.

The buttons in the IDE and WPILib's commands are all just Gradle underneath. If a button breaks, the same thing works from a terminal. On Windows it's gradlew.bat; on Mac and Linux it's ./gradlew. The first build downloads a lot, so it's slow once.

Gradle

Five commands cover almost everything

CommandWhat it does
gradlew buildCompile and test everything
gradlew testRun only the tests
gradlew runStart the program in the simulator
gradlew run -PhwSimDrive the real chassis from this laptop
gradlew deploySend the program to the robot

On Windows: gradlew.bat. In the IDE, the run buttons do the same thing for you.

-PhwSim is the bench trick: the laptop runs the robot program, and the CANivore plugged into USB carries its commands to the real motors. No robot computer, no radio. Deploy comes later, once the Systemcore arrives.

IntelliJ IDEA: built for Java and Gradle. What most Java companies use.

VS Code with WPILib’s extension: what FIRST’s docs show.

Both work: our projects come set up for either one. IntelliJ understands Java and Gradle out of the box. VS Code needs Microsoft's Java extensions plus WPILib's, and one restart after installing them. In either one, run the program through the project's run tasks or buttons, not the Run link next to main: that skips WPILib's native libraries.

Version control

What did we change, who changed it, and how do we undo it?

Git answers all three. Every professional software team uses it.

Picture the night before competition: the robot drove fine yesterday, today it doesn't, and four people edited the code. Without version control you're guessing. With it, you see exactly which lines changed, by whom, and you can go back to yesterday's version in one command.

Commits

A commit is a save point with a note

Mon · Sam

One motor spins from the stick

Wed · Ana

Limit the motor to 20%

Sat · Sam

Button A points the wheel ahead

Each commit records the whole project as it was, who made it, when, and why.

Commit small and often. A good note says what changed: “Limit the motor to 20%”, not “stuff”.

The names are made up. The point: history is a list of small, described steps. If Wednesday's change broke something, you can see exactly what it changed and undo just that. In the IDE, the Commit window shows what changed, you type the note, click Commit.

GitHub

pull →

A teammate’s

Git is the tool; GitHub is a website that hosts the shared copy. Commits live on your laptop until you push. Pull before you start work, push when you've committed something that works.

Branches

Try things without breaking the robot

main: always works

lock-wheels: your experiment

merged

A branch is your own line of commits. main keeps working while you try something.

When it works, it’s merged back into main. If it doesn’t, throw the branch away.

This is how two people work on the robot at once without stepping on each other: each on their own branch. Rule for the team: never commit straight to main; main is what goes on the robot.

Pull requests

Ask before your branch joins main

1

Push your branch

Your commits go up to GitHub.

2

Open a pull request

“Please merge this into main”, with what and why.

3

Review

Teammates read the changes, comment, ask questions. Checks run.

4

Merge

Approved and green: it joins main.

A second pair of eyes catches what you can’t see in your own code. Every company works this way.

Review is a conversation, not a grade. Reading other people's pull requests is one of the fastest ways to learn. The team has agreed to automated AI reviews on pull requests too; they leave comments like a reviewer would, and a person still decides.

Testing

Code that checks your code

@Test
void fullStickIsTwentyPercent() {
  gamepad.setLeftY(-1.0);
  robot.teleopPeriodic();
  assertThat(motorOutput())
    .isEqualTo(0.2);
}

Set it up, do it, check the result. Every test has those three parts.

Thousands of tests run in seconds, with no robot. Break something and a test says exactly what.

The example is simplified, but it's the real idea: pretend the stick is pushed all the way, run one loop of the robot program, and check the motor was told 20%. If someone later changes the 0.2 by accident, this test fails before it ever reaches the robot.

CI/CD and GitHub Actions

A robot checks every change for you

CI: continuous integration

Every push and pull request, a fresh computer in the cloud builds the code and runs every test.

GitHub Actions

GitHub’s service that runs those checks. A small file in the project says what to run.

CD: continuous delivery

Shipping passing code automatically. For a robot, we still deploy by hand.

Green check: it builds and every test passes on a clean machine.

Red X: something broke. Fix it before merging.

The point of the clean machine: it proves the code works from a fresh copy, not just on the laptop where you've been fiddling. "Works on my machine" stops being an excuse. Rule: nothing merges into main with a red X.

Releases

Lock down exactly what goes on the robot

1

Tag a commit

Give one exact commit on main a version name, like week1-v3.

2

Build it once

CI builds and tests that tag on a clean machine. Same tag, same program, every time.

3

Deploy the release

At an event, only releases go on the robot. New work waits for the next one.

Something breaks? Put the last good release back on in minutes.

Every library we use is a release too: WPILib 2027.0.0-alpha-7.

Between matches is the worst time to discover someone's half-finished change is on the robot. A release fixes that: everyone knows exactly which code is running, the log says which version, and going back is one deploy. The same idea is why the libraries have version numbers: the build asks for an exact version, so it builds the same on every laptop, today and next year.

Where it runs

Three places to run the same program

Simulator

Any laptop, no hardware. Pretend motors and a pretend field.

gradlew run

Bench

The laptop drives real motors through the CANivore. Chassis on blocks.

gradlew run -PhwSim

Robot

The program goes onto the robot’s own computer. Driven from the Driver Station.

gradlew deploy

Same code in all three. The simulator is where most work happens; the bench is where we prove it on real motors; the robot is last. The robot's computer, the Systemcore, arrives in late November, so for now it's the first two.
